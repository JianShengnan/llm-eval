# 能力边界：五项需求的覆盖度对照

> 结论速查：**5 项里完全覆盖 2 项、部分覆盖 1 项、不覆盖 2 项。**
> 不覆盖的两项（数据处理、模型训练）不是缺口，而是评测框架本就不该承担的职责 ——
> 但需要你按正确的预期排期，别以为一套框架能端到端包住整条链路。

| # | 需求 | 覆盖度 | 一句话说明 |
| :- | :--- | :--- | :--- |
| 1 | 通用能力评测（盘古7B / Qwen8B / Qwen3-32B） | ✅ 完全支持 | 已就绪，填 `base_url` 即可跑 |
| 2 | 数据清洗 → 泛化 → 训练集/验证集 | ❌ 不支持 | 需独立数据处理管线；框架只能补「泄漏检测」这一小块 |
| 3 | 盘古7B / Qwen8B 微调训练 | ❌ 不支持 | 需 LLaMA-Factory / ms-swift / PEFT，且需要 GPU 机器 |
| 4 | 通用能力评测（微调后 3 对象） | ✅ 完全支持 | 含 pre→post 配对显著性检验与退化判定 |
| 5 | 专业能力测评（5 个对象） | ⚠️ 部分支持 | 抽象层/统计层/报告层已备，专业指标与业务数据待补 |

---

## 1. 通用能力评测（微调前）— 完全支持

**现状**：可直接执行。

```bash
cp config.example.json config.json     # 填三个模型的 base_url / model
python -m geval probe  --config config.json
python -m geval run    --config config.json --smoke --limit 8 --models pangu7b-pre,qwen8b-pre,qwen3-32b
python -m geval run    --config config.json --limit 40 --models pangu7b-pre,qwen8b-pre,qwen3-32b
python -m geval run    --config config.json --models pangu7b-pre,qwen8b-pre,qwen3-32b
```

**已具备**：8 类评测任务（C-Eval / CMMLU / MMLU / MMLU-Pro / ARC / AGIEval / GSM8K / BBH / IFEval / JSON-Schema）、
三种 prompt 协议消融、三种打分路径（gen / logprob / loglikelihood）、
置信区间与配对显著性检验、时延分布、解析质量诊断、自包含 HTML 报告。

**前置条件**（不是框架能力问题，是数据问题）：
- 联网机器跑 `scripts/prepare_datasets.py` 把公开基准转成 JSONL，拷进内网
- 三个模型已在 vLLM 上服务化，且暴露 `/v1/chat/completions`（要 `acc_norm` 还需 `/v1/completions`）

**可选增强**：离线部署 `lm-eval` 出一个可对标公开榜单的「锚点数字」，
与 geval 结果比对偏移量。步骤见 `docs/OFFLINE_DEPLOY.md`。

## 2. 数据清洗与泛化切分 — 不支持

**这一项要交给独立的处理管线，不要指望评测框架。**

评测框架与数据处理框架的职责是正交的：前者回答「模型有多强」，后者回答「数据有多干净」。
把两者揉进一套工具，结果是两边都做不好。

### 框架能做的（极其有限，但有一点很关键）

| 能力 | 状态 | 说明 |
| :--- | :--- | :--- |
| 题面去重 | ✅ 已有 | `datasets.dedupe()`，防止同一题重复计入导致分数虚高 |
| 多格式归一化 | ✅ 已有 | 自动吸收 C-Eval / CMMLU / MMLU / GSM8K 等不同字段命名 |
| 分层抽样 | ✅ 已有 | 评测阶段按 subject 等比抽样 |
| **训练/测试集泄漏检测** | ❌ **待实现** | **这是框架最该补的一块**，见下 |

### 建议补的：`geval audit`（训练/测试集泄漏检测）

这是评测框架**唯一**能对数据处理提供实质约束的地方，而且风险最高：
测试集一旦被污染，后面所有数字全部失效，且**从分数上完全看不出来**。

建议实现的检查项：

1. **精确重复**：训练集题面（归一化后）与 test 集完全相同的条目
2. **近似重复**：编辑距离 / 3-gram Jaccard 超阈值的条目（模板化生成的数据很容易撞）
3. **标签冲突**：同一题面在 train 与 test 中标注不同意图
4. **答案泄漏**：test 题面出现在训练集的 `output`/`label` 字段里
5. **指纹记录**：test 集 sha256 写入 manifest，保证多次运行用的是同一份

### 数据处理管线本身需要覆盖的（与本框架无关）

去重、纠错、低质过滤、噪声清洗、标注一致性校验、标注冲突仲裁、
同义改写增强、模板扩增、类别均衡、难例挖掘、train/val/test 切分与冻结。

## 3. 微调训练 — 不支持

**框架是纯评测的，不含任何训练代码。** 这是刻意的边界。

### 工具选型

| 工具 | 定位 | 适配场景 |
| :--- | :--- | :--- |
| **LLaMA-Factory** | 中文社区主流 SFT 框架 | LoRA / QLoRA / 全参，WebUI + CLI，模型覆盖面广 |
| **ms-swift** | 阿里魔搭 | 与 EvalScope 训练-评测闭环，如果走 EvalScope 可优先 |
| **PEFT + transformers** | 原生方案 | 需求简单、想完全掌控训练细节时用 |

盘古7B 是相对少见的基座，**优先确认所选框架是否已内置它的适配**；
没有的话用 `PEFT + transformers` 手工接更稳。

### ⚠️ 环境约束（这一条可能影响整体排期）

运行环境是**内网 Linux ARM64 单机**。而模型训练通常需要 NVIDIA GPU，
**ARM64 + GPU 的驱动与 CUDA wheel 生态要窄得多**，很多训练框架在 aarch64 上装不起来。

需要先确认：

- 这台 ARM64 机器有没有 GPU？什么型号？
- 如果没有，微调是否在另一台 x86 + GPU 机器上做？
- 如果微调在别处做，评测仍在内网 ARM64 上跑 —— 两边通过网络传模型产物或直接调 API 评测

**评测与服务化部署在 ARM64 上没问题**（纯 Python + vLLM 的 ARM64 支持较好）；
**训练大概率要换机器**。这件事建议尽早确认，不要等排到阶段 3 才发现。

### 与评测的衔接点（容易漏）

微调产出物必须**完整保留 `tokenizer_config.json`**（其中含 `chat_template`）。
原因见 `README.md` §7：模板一旦静默变更或丢失，
微调后的模型会因格式不匹配而全面掉点，现象和「灾难性遗忘」完全一样，
会让你误判成「微调把模型搞坏了」。

## 4. 通用能力评测（微调后）— 完全支持

**现状**：可直接执行，且报告会自动产出 pre→post 对比。

```bash
# 微调完成后，起好两个新端点（config.json 里已定义 pangu7b-post / qwen8b-post）
python -m geval run --config config.json --resume
```

报告第 4 节「微调影响评估」逐任务给出：

- 微调前 / 微调后 / 差值（约定为 **post - pre**）/ 95% 置信区间 / McNemar p 值
- 判定：**显著退化 / 显著提升 / 不显著（视为持平）**
- 汇总：宏平均变化、显著退化任务列表、显著提升任务列表

**内置的可比性守卫**（配对检验的前提）：
样本覆盖率 < 90%、两模型的 `protocol` / `mode` / `num_fewshot` 不一致、
样本数差异 > 10% —— 任一条触发即在表内出告警行，标记该行结论不可用。

**必须人工确认一条**：微调是否改动了 `chat_template`。框架抓不到（发生在推理服务层）。

## 5. 专业能力测评（5 个对象）— 部分支持

**架子已经打好，缺的是专业指标与业务数据。**

### 已具备

| 能力 | 说明 |
| :--- | :--- |
| 任务注册机制 | `geval/tasks.py::TASK_REGISTRY`，加一个子类即可接入新任务 |
| `json_schema` 任务 | 已实现四层指标：JSON 可解析率 / Schema 通过率 / 意图准确率 / 槽位完全一致率 |
| 答案抽取层 | JSON 提取（含围栏、花括号配平、尾逗号修复）、思维链剥离 |
| 统计与报告层 | Wilson / bootstrap 区间、McNemar 精确检验、配对 bootstrap、分组明细、错例抽样 |
| 配对对比 | 5 个对象的任意两两配对显著性检验 |
| 示例数据集 | `datasets/json_schema/` 含 16 条意图+槽位样本与 `schema.json` |

### 待补（这是阶段 4 的主要开发工作）

**专业指标**（通用能力不需要，但专业能力必须有）：

| 指标 | 为什么必须 | 现状 |
| :--- | :--- | :--- |
| **意图混淆矩阵** | 定位是哪两个意图在互相打架，是最高价值的诊断产出 | ❌ 待实现 |
| **槽位 F1** | 精确匹配过严，F1 更能反映实际可用性 | ❌ 待实现（仅有完全一致率） |
| **幻觉槽位率** | 用户没说却填了槽位 → 下游直接出错 | ❌ 待实现 |
| **拒识率 / 误触发率** | 模糊输入该不该兜底，是线上投诉主因 | ❌ 待实现 |
| **P99 时延与单样本成本** | 决定能否替代 32B，是你引入小模型的初衷 | ⚠️ 已有单请求时延，级联场景需加权 |
| 级联路由指标 | 初筛命中率 / 升级率 / **路由错误率**（最致命）/ 级联端到端准确率 | ❌ 待实现（若做级联架构） |

**业务数据**：

- 需要你提供**真实业务标注的意图识别测试集**（含模糊输入、多意图、拒识样本）
- 必须包含**难例与边界样本**，否则测出来的准确率虚高、上线后投诉
- 测试集需冻结并记录 sha256
- 当前仓库里只有 16 条示例，仅够验证链路，不构成评测

### 工作量参考

框架侧：新增 1 个任务类 + 混淆矩阵渲染 + 4 项指标计算，属于**中等规模改动**，
抽取层/统计层/报告层全部可复用。

数据侧：取决于你的标注进度，**这是真正的瓶颈**，且不受框架影响。

## 关键前置确认项

排期前建议先把这三件事定下来：

1. **微调在哪台机器做？** 有没有可用的 GPU？ARM64 单机大概率不适合训练。
2. **专业能力测试集从哪来、什么时候能冻结？** 这是阶段 4 的唯一瓶颈。
3. **微调时是否会改动 `chat_template`？** 建议从第一次训练就固定住。
