# 评测方法论说明：与开源框架的关系、可比性边界、专业能力测评设计

> 这份文档回答三个问题：
> 1. geval 与主流开源评测框架是什么关系？差距在哪？
> 2. 我跑出来的数字，哪些能和公开榜单对齐，哪些不能？
> 3. 后续的**专业能力测评**该怎么做？

---

## 1. 直接结论

**geval 没有基于任何开源框架，是自建实现。** 但其中使用的**基准数据集与指标定义是主流的**。

分两层看这件事：

| 层面 | 情况 | 评价 |
| :--- | :--- | :--- |
| **基准（benchmark）** | C-Eval、CMMLU、MMLU、MMLU-Pro、ARC、GSM8K、BBH、IFEval | ✅ 完全主流，与 OpenCompass / EvalScope / lm-eval 用的是同一批题 |
| **指标定义** | acc、acc_norm（长度归一化续写似然）、EM、IFEval prompt-level / instruction-level 准确率 | ✅ 与 lm-eval / IFEval 官方口径一致 |
| **统计方法** | Wilson 区间、bootstrap CI、McNemar 精确检验、配对 bootstrap | ✅ 比多数开源框架更严格（多数框架只给点估计） |
| **实现（harness）** | 自研 | ❌ **非主流**，没有第三方验证，模板细节自带偏差 |

所以准确的说法是：**评测方法主流，评测框架自建。** 这两件事必须分开说，不能混为一谈。

**为什么当时选择自建**：目标环境是内网 Linux ARM64、无外网、无 pip 源，
加之你此前在 TOMP 项目上确立过「零第三方依赖、拷目录即可部署」的工程标准。
geval 运行时只依赖 20 个标准库模块（`scripts/verify_deps.py` 可验证）。

> **⚠️ 修正（同日）**：你后续澄清**依赖可以从外网下载后导入内网**。
> 因此「离线」这条理由**不再成立**，上面的取舍依据已被推翻。
>
> 经核实：`lm-eval` 的基础依赖里**不含 torch**（torch 只在 `[hf]` extra 中），
> 评测 OpenAI 兼容端点只需 `[api]` extra，全部有 aarch64 wheel 或为纯 Python 包；
> EvalScope 同样无 torch 但基础依赖含 transformers，较重。**离线部署完全可行。**
>
> **修正后的结论：阶段 1 的正式数字改用 lm-eval 出，geval 退回到它不可替代的位置**
> （prompt 消融、微调前后配对检验、专业能力测评）。详见
> [`OFFLINE_DEPLOY.md`](OFFLINE_DEPLOY.md)（离线部署实操）与本文 §6。

**代价是真实的**，见第 3 节。这个取舍本该在动手前就和你确认，是我的问题。

## 2. 三大主流框架现状（2026-09）

| 框架 | 出品方 | 定位 | 开源协议 | 规模 | 关键特点 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **lm-evaluation-harness** | EleutherAI | 学术标准 / 论文复现 | MIT | 400+ 任务 | HuggingFace Open LLM Leaderboard 官方后端；几乎所有模型技术报告都用它出分 |
| **OpenCompass** | 上海 AI Lab | 中文评测最全 | Apache-2.0 | 70+ 数据集 / 约 40 万题 | C-Eval 首创者；中文与长上下文覆盖最强；2026-04 起多模态能力移交 VLMEvalKit |
| **EvalScope** | 阿里魔搭 | 一站式评测 + 压测 | Apache-2.0 | 100+ 数据集 | **原生支持 OpenAI 兼容 API 评测**（`--eval-type openai_api`）；唯一带性能压测；与 ms-swift 训练闭环 |
| HELM | Stanford CRFM | 多维评估方法论 | Apache-2.0 | — | 精度 / 偏见 / 毒性 / 效率多维度，学术严谨但操作重 |

**对你这个场景最关键的一条**：EvalScope 可以直接评测一个 OpenAI 兼容的推理服务端点，
一条命令就能评你内网 vLLM 起的三个模型——**不需要下载模型权重，不需要 GPU 在本机**：

```bash
# 在能联网、能访问内网模型端点的机器上
pip install evalscope

evalscope eval \
  --model pangu-7b-instruct \
  --api-url http://<内网IP>:8001/v1 \
  --api-key EMPTY \
  --eval-type openai_api \
  --datasets ceval cmmlu gsm8k  \
  --limit 200
```

这意味着「用不用开源框架」并不是一个非此即彼的选择：**你完全可以两套都跑。**

## 3. geval 与开源框架的能力对照（诚实版）

| 能力 | geval | 开源框架 | 差距影响 |
| :--- | :--- | :--- | :--- |
| C-Eval / CMMLU / MMLU / GSM8K / BBH / IFEval | ✅ | ✅ | 无 |
| 基准数量 | 12 个任务 | 100~400+ | 小，你的场景不需要全跑 |
| **acc / acc_norm 续写似然打分** | ✅ 已实现（`mode: loglikelihood`） | ✅ lm-eval 主指标 | **已补齐**，见 §4 |
| 首 token logprob 打分 | ✅ `mode: logprob` | ⚠️ 部分支持 | 无 |
| **prompt 模板与榜单完全一致** | ❌ 近似 | ✅ 官方模板 | **无法直接对齐榜单数字**，见 §5 |
| HuggingFace 权重直评（`--model hf`） | ❌ 只能走 API | ✅ | 无实际影响（你的模型本来就是服务化部署） |
| 多模态 / 长上下文 / 代码 / Agent 评测 | ❌ | ✅ | 你的场景不需要 |
| 性能压测（TTFT / P99 / 吞吐） | ⚠️ 只记单请求时延 | ✅ EvalScope 独有 | 建议单独用压测工具补 |
| Web Dashboard / 可视化 | ✅ 自包含 HTML + 内联 SVG | ✅ | 无（离线环境反而更有优势） |
| **第三方验证 / 社区审计** | ❌ **无** | ✅ | **真实风险**：可能存在未发现的实现 bug |
| 统计显著性检验 | ✅ McNemar + 配对 bootstrap | ⚠️ 多数只给点估计 | geval 更强 |
| 断点续跑 / 磁盘缓存 / 代理控制 | ✅ | ⚠️ 部分支持 | geval 更强 |
| 零依赖离线部署 | ✅ | ❌ 均需 pip 安装 | geval 更强 |

关于「未发现的实现 bug」这一条我不是随口说的：geval 自检在上线前抓出了 6 个真实缺陷，
其中一个是任务类漏定义 `name` 导致被喂错数据集、IFEval 与 JSON 任务全部得 0 分——
**如果没有自检，这个 bug 会被当成「小模型结构化输出能力为零」汇报给你。**
这说明自建 harness 的风险是实打实的，也说明它必须配自检才能用。

## 4. `acc` / `acc_norm` 已实现（与 lm-eval 口径对齐）

选择题有三种打分路径，配置在任务的 `mode` 字段：

| mode | 机制 | 请求数 | 用途 |
| :--- | :--- | :--- | :--- |
| `gen`（默认） | 生成文本后抽取选项字母 | 1 / 样本 | 日常全量、与 ChatGPT 类用法一致 |
| `logprob` | 读首生成位置的 top_logprobs 取 argmax | 1 / 样本 | 降低小模型「输出跑偏字母」的噪声 |
| `loglikelihood` | `/completions` + `echo` 取续写 token 级 logprob，算 **acc** 与 **acc_norm** | N 选项 / 样本 | **与 lm-eval / 公开榜单口径对齐** |

`loglikelihood` 模式的关键点：

- `acc` = 续写 logprob 之和最大者
- `acc_norm` = **长度归一化**后续写 logprob 最大者（lm-eval 在选择题上的主指标）
- 长度归一化不是细节而是关键：否则「续写越长 logprob 越低」会让短选项系统性占优
- 边界处理：续写被分词器切成 `[" ", "A"]` 时，空格属于续写的一部分，
  必须一起计入（`client._sum_continuation` 显式处理）；这条规则由自检中的
  纯数学校验覆盖，不依赖真实服务即可验证
- 报告与逐样本明细同时记录 `acc_choice` / `acc_norm_choice` / `acc_norm_margin`，
  两者不一致的样本正是「格式偏好」而非「知识差异」的候选，值得单独看

配置示例：

```json
{ "name": "ceval", "tag": "ceval-likelihood", "mode": "loglikelihood", "primary": "acc_norm", "num_fewshot": 5 }
```

代价要清楚：4 选项 = 每个样本 4 次请求。所以建议**对 C-Eval / MMLU 这类选择题抽样跑
`loglikelihood` 出对标数字，全量仍用 `gen`**。

## 5. 可比性边界：哪些数字能用，哪些不能

这是最容易被误用的一节。

| 你的数字 | 能否与公开榜单比较 | 说明 |
| :--- | :--- | :--- |
| geval 内部模型间的**相对差距** | ✅ 可以 | 同模板、同参数、同样本，横向比较是有效的 |
| 微调**前 vs 后**的差值 | ✅ 可以 | 这是配对比较，模板偏差被抵消 |
| `json_schema` / `ifeval` 等自建任务 | ✅ 可以 | 没有外部榜单可对标，但内部对比有效 |
| **与公开榜单的绝对值** | ❌ **不可以** | 模板、few-shot 采样、抽取规则、分词边界都不同，选择题上模板敏感度可达数个百分点 |
| 「我们比某模型高 3 分」这类对外结论 | ❌ 不可以 | 除非用开源框架或官方模板重跑 |

**如果必须给出可对外引用的数字**：用 EvalScope / OpenCompass 跑同一批题，
把它的分数当作锚点，再对照 geval 的分数算出偏移量。偏移量稳定之后，
geval 的日常数字就有了可解释性。这比"换框架"更省事，也更准确。

## 6. 推荐方案：混合，而不是二选一

> **前提已更新**：既然依赖可以导入内网，下面的「锚点层」可以直接部署在内网机器上（不联网也能跑），
> 不必单独找一台能联网的机器。部署步骤见 [`OFFLINE_DEPLOY.md`](OFFLINE_DEPLOY.md)。

```
┌─────────────────────────────────────────────────────────────┐
│ 锚点层（内网机器，离线部署 lm-eval）                          │
│   lm_eval --model local-completions                        │
│   → 产出可对标公开榜单的「官方口径」数字（acc / acc_norm）     │
│   → 阶段 1 汇报、对外引用、模型选型的最终依据                 │
├─────────────────────────────────────────────────────────────┤
│ 日常层（同一台内网机器，geval）                               │
│   python -m geval run / report                             │
│   → prompt 协议消融、微调前后配对对比、分组短板定位            │
│   → 带显著性检验，成本低、可反复跑                            │
├─────────────────────────────────────────────────────────────┤
│ 校准：两套跑同一批样本（limit 200），算偏移量，用锚点解释日常数字 │
└─────────────────────────────────────────────────────────────┘
```

### 落地顺序

```bash
# ① 联网机器：下载轮子（只下 [api,ifeval]，不要 [hf]，避免引入 torch）
bash scripts/download_wheels.sh bootstrap
bash scripts/download_wheels.sh lm-eval

# ② 内网机器：离线安装
bash scripts/install_offline.sh wheels/bootstrap wheels/lm-eval --venv /opt/evalenv --bootstrap

# ③ 别忘了数据集也要离线（见 OFFLINE_DEPLOY.md 坑 1，比轮子更容易翻车）
export HF_DATASETS_OFFLINE=1 HF_HUB_OFFLINE=1

# ④ 三模型 × 四个基准，出锚点数字
/opt/evalenv/bin/lm_eval --model local-completions \
  --model_args model=<模型名>,base_url=http://127.0.0.1:8001/v1/completions,num_concurrent=16 \
  --tasks ceval-valid,cmmlu,mmlu,gsm8k --num_fewshot 5 \
  --output_path ./lmeval_out/<模型名>

# ⑤ 同批样本用 geval 对齐口径
python -m geval run --config config.json --tasks ceval-likelihood --limit 200

# ⑥ 比对偏移量，稳定后（通常 1~3 个点）阶段 1.5 / 阶段 4 全部用 geval 看相对变化
```

### 各管一段（这是重点）

| 需求 | 用什么 | 理由 |
| :--- | :--- | :--- |
| 阶段 1 正式数字 | **lm-eval** | 官方模板、社区验证、与榜单同口径 |
| 阶段 1 prompt 协议消融 | geval | 改 JSON 即可，不用动框架配置；带配对显著性 |
| 阶段 1.5 微调前后配对对比 | geval | 没有框架会做「你的模型 A vs 你的模型 B 的 McNemar 检验」 |
| 阶段 4 专业能力测评 | geval | 开源框架没有你的业务数据与指标定义 |
| 性能压测（TTFT / P99 / 吞吐） | EvalScope `perf` 或 vLLM bench | lm-eval 不做压测 |

geval 并没有白写：它的抽取层、统计层、报告层可以直接复用到阶段 4，
而那部分**开源框架结构上就帮不上忙**。被替换掉的只是「通用基准的绝对值」这一块。

### 通用能力评测的 5 个对象

阶段 1 与阶段 1.5 合起来，构成一次完整的 **5 对象通用能力对比**
（盘古7B 微调前/后、Qwen8B 微调前/后、Qwen3-32B）。分两个时点跑，但**必须用同一套配置、同一批样本**：

```bash
# 阶段 1（微调前，3 个）
python -m geval run --config config.json --models pangu7b-pre,qwen8b-pre,qwen3-32b --resume

# 阶段 1.5（微调后，补齐 2 个 post，报告自动出退化对比）
python -m geval run --config config.json --resume
```

两点在开源框架上要特别注意：

1. **lm-eval 不做跨模型的配对显著性检验。** 它能给你 5 组分数，
   但「微调后掉的这 2 个点是不是噪声」需要自己算。
   geval 的报告直接给出 McNemar p 值与差值置信区间 —— 这是它在这个阶段仍然不可替代的原因。
2. **两次 lm-eval 运行的 few-shot 示例必须完全一致**（同样的 `--num_fewshot` 且示例抽样可复现），
   否则 pre→post 的差值里混入示例差异。lm-eval 的 few-shot 示例来自数据集固定位置，
   通常没问题，但换任务版本或升框架版本后要重新确认。

> **⚠️ chat template 是配对对比最大的隐藏风险。** 详见 README §7。
> SFT 若改动了模板，同一段 prompt 在两个模型上被拼成不同的实际输入，
> 差值方向不可预期 —— 而且这种污染**在配置层面完全看不出来**，
> 必须人工确认（对两个端点各发一条相同请求，比对服务端日志里的最终拼串）。
> 最省事的规避方式：微调时不要改 chat template。

## 7. 专业能力测评（阶段 4）该怎么做

**结论：开源框架在这里帮不上忙，必须自建 —— 而且 geval 的架构就是为这一步准备的。**

原因很直接：开源框架内置的是公开榜单（MMLU、C-Eval……），没有任何框架会内置你的意图体系、
你的槽位定义、你的模糊输入处理规范。你的专业能力测试集**只能来自你自己的业务标注数据**。

### 7.1 与通用能力测评的本质差异

| 维度 | 通用能力 | 专业能力（意图识别） |
| :--- | :--- | :--- |
| 数据来源 | 公开基准，可下载 | **只能自建**，来自业务标注 |
| 是否可对标外部 | 部分可以 | **完全不可对标**，只看前后变化 |
| 主指标 | 准确率 | 准确率 + 槽位 F1 + 拒识率 + 误触发率 |
| 关键失败模式 | 答错 | **幻觉槽位**、**意图串位**、**该拒识却硬答** |
| 混淆结构 | 无 | **意图混淆矩阵是核心产出** |
| 成本约束 | 不敏感 | **P99 时延与单次成本是硬指标** |

### 7.2 必须测的指标清单

| 指标 | 为什么必须测 | geval 中如何落地 |
| :--- | :--- | :--- |
| 意图准确率 | 基础 | `json_schema` 任务的 `intent_accuracy` |
| 槽位完全一致率 / 槽位 F1 | 精确匹配过严，F1 更能反映实际可用性 | `slots_exact_rate` 已有；F1 需新增（见下） |
| **幻觉槽位率** | 用户没说却填了槽位 → 下游直接出错 | 新增：`slots ⊆ gold` 检查 |
| **拒识率 / 误触发率** | 模糊输入该不该兜底，是线上投诉主因 | 新增：区分「该拒识」与「该答」两类样本 |
| **意图混淆矩阵** | 定位是哪两个意图在打架 | 新增：报告输出 N×N 矩阵 |
| 结构合法率 | 见通用能力：失败多在第一层 | `json_valid_rate` 已有 |
| P50 / P95 / P99 时延 | 时效性是你引入小模型的初衷之一 | 已有；级联场景需端到端统计 |
| 单样本成本（token 量） | 决定能否替代 32B | `tokens` 统计已有 |

### 7.3 如果做级联架构（小模型初筛 + 32B 精识别）

这是你正在探索的方向，评测对象会从「单模型」变成「路由系统」。要额外测：

| 指标 | 含义 |
| :--- | :--- |
| **初筛命中率** | 小模型能独立搞定的比例（决定成本节省幅度） |
| **升级率** | 需要送 32B 的比例（直接决定成本） |
| **级联端到端准确率** | 最终用户感知的准确率，而非单模型准确率 |
| **路由错误率** | 小模型把本该升级的样本「自信地答错」的比例 ← **最致命** |
| 级联平均时延 / 成本 | 需按升级率加权，不能只算单模型 |

注意：**级联的收益来自「小模型答对的那些样本省下了 32B 的调用」**，所以
「小模型在自身置信阈值以上的准确率」比「小模型整体准确率」重要得多。
这需要给测试集加置信度分层，是通用能力测评完全没有的维度。

### 7.4 落地路径

geval 的扩展点是 `geval/tasks.py::TASK_REGISTRY`，加一个任务子类即可：

```python
class IntentEvalTask(BaseTask):
    name = "intent_eval"
    kind = "json"

    def run_one(self, item, client):
        # 1. 复用 JSONSchemaTask 的结构合法性 / schema 校验
        # 2. 追加：槽位 F1、幻觉槽位（slots ⊆ gold）、拒识分支判定
        # 3. 记录 confusion：gold_intent -> pred_intent
        ...
```

然后 `report.py` 增加混淆矩阵与拒识分支的小节即可。**阶段 1 建立的抽取层、
统计层、报告层可以完整复用**，只需要新增专业指标的计算。

### 7.5 阶段 4 的评测对象与对比口径

你要比的是 5 个对象，但**核心问题只有一个**：

> 微调后的 7B/8B，在专业任务上能否追平 32B？代价是多少通用能力？

所以阶段 4 的报告应该是**一张二维表**：

| 模型 | 专业准确率 | 槽位 F1 | 通用能力退化 | P99 时延 | 单样本成本 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 盘古7B-pre | 低 | 低 | 基线 | 最低 | 最低 |
| 盘古7B-post | **↑?** | **↑?** | **↓?** | 最低 | 最低 |
